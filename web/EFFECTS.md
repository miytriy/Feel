# エフェクト・アニメーションの規約(高画質 × 高フレームレート)

Feel のすべてのエフェクト・アニメーションは、スマホでも60fps以上で、高画質に動くこと。軽いゲームなので、「重いから簡素にする」は理由にしない。重い処理は **事前に画像へ焼き込む** ことで、見た目を落とさずに軽くする。

## 守ること
1. **動かしていいのは `transform`(位置・拡大・回転)と `opacity`(不透明度)だけ。** GPUだけで合成され、再描画も再レイアウトも起きない。
2. **動かしてはいけないもの**(アニメ中に毎フレーム再計算・再描画になる):
   - `filter`(blur / brightness / drop-shadow)のアニメーション
   - `box-shadow` / `background` / `background-position` / `border` の変化
   - `width` / `height` / `top` / `left` / `margin` の変化(→ `transform: translate/scale` にする)
   - SVGフィルター(`feTurbulence`・`feDisplacementMap` など)を、動いている要素にかけること
   - SMIL(`<animate>`)でフィルターの値を毎フレーム変えること
3. **複雑な質感は、事前に画像(WebP・透過)に焼き込む。** 煙・炎・電気・もや・光の揺らぎなど。
   - 解像度は表示サイズの2〜3倍(DPR対応)。
   - 形が変わる動きは、違う模様の画像を数枚重ねて、順にクロスフェード(opacity)+ごくゆっくり漂わせる(transform)。
   - 焼き込みに使うフィルターは、画像を作る時だけ使う(ゲーム実行中には使わない)。
4. 色の見た目をアニメで変えたいときは、変化させたい見た目の層を別に重ねて、その層の opacity を動かす(例: 明るさのフラッシュ = 白い層の opacity)。
5. 動く層には `will-change: transform, opacity` を付ける(常時動くものだけ。付けすぎない)。
6. 画像の置き場所: ゲーム内は `web/public/fx/`、ルール画面の動画は `web/public/rules/`。
7. ルール画面などに載せる動画は、GIFにしない。**60fps・2倍解像度のMP4**(`<video autoplay loop muted playsinline>`)にする。
   - CSSアニメだけの場面は、`document.getAnimations()` で時間を止め、1/60秒ずつ進めて1コマずつスクリーンショット → `ffmpeg -framerate 60` でMP4にする(確実に60fps)。
   - タイマーで動く場面は、CDPスクリーンキャストで撮る(ヘッドレスでは約30fpsが上限なので、その旨を明記する)。

## 例外(許容していること)
- 一度きり(1秒未満)の演出で、フィルターを使うもの(消滅の電気の輪など)は、まだ焼き込んでいない。見直すときは上の方法で画像化する。
- ダメージなどの文字の虹色(`feel-rainbow`)は、`background-position` を動かしている。小さな文字だけなので残している。

## 消滅の作り直し(11/8): 60fpsの連番画像
- 消滅は、SVGフィルター・ずらしのアニメを全部やめて、**56コマ(0.9秒 = 約62fps)の連番画像**を、1コマずつ見せるだけにした。画像は `public/fx/vanish/sheet.webp`(8列×7行、1コマ400px = 表示の約1.4倍)。
- コマ送りは、1コマ分(約290px)の小さな四角の中で、背景の位置だけを `steps()` でずらす(`src/VanishFx.jsx`: 行 `vx-y` + 列 `vx-x`)。※例外: この1か所だけ `transform` ではなく `background-position`。理由: シート全体(約2300×2000px)を `transform` で動かす作りは、スマホで巨大なレイヤー(3倍の解像度で約7000×6000px)になり、**何も表示されなくなった**(11/8 22:51、実機で「882msで消滅エフェクトが出なくなった」)。小さな四角の背景なら、レイヤーは小さく、再描画も軽い。コマの中身は、上の「消滅」の動き(割合)を、`tools/bake-vanish.cjs` が1コマずつ書き出したもの。動きの元の定義は `tools/vanish-keyframes.css`。
- 作り直す・変えるときは、`tools/bake-vanish.cjs` を実行する(playwright と python3 + PIL が必要)。長さは `VANISH_SLOW`(BattleScreen.jsx)で変えると、同じコマを速く/遅く送る。ライブのSVGフィルターや、CSSで重ねる作りには戻さない。
- 計測(テスト用ブラウザ。倍率3倍): 5体同時でも約61コマ/秒(最大の止まり17ms。作り直す前は約19コマ/秒、最大190ms)。1回の再生は約896ms、見えたコマは57種。
- 端末で実際に何msかかったかは、テスト戦の画面の上に「消滅 ◯◯◯ms」と出る。

## 消滅の表示を canvas に変更(11/9)
- 症状: ときどき「めっちゃ速く再生される」「途切れる」(PC)。推測の原因: 約3200×2800pxの画像のデコードで画面が固まり、その間も時計だけ進む/背景位置のアニメで再描画が走る。

- 見た目・長さ(0.9秒、56コマ)・画像は変えていない。実機での確認はこれから。計測: テスト戦の「消滅 ◯◯◯ms」。

## 軽い演出の重ね(試験・11/23)
- 設定「軽い演出(回復・強化・カウントダウンなど)は、終わるのを待たずに次の演出を流す(試験)」(初期値オン)。対象は `LIGHT_FX` = heal / buff / keyword / countdown だけのまとまり。ダメージ・召喚・破壊・必殺・進化は、今までどおり最後まで待つ。
- まとまりの待ち時間を `LIGHT_RATIO`(0.4)倍にして次へ進む。演出そのものは、本来の長さまで続ける(`lingerRef`: ユニットごとに、続けるfx・出した時点のtick・終わる時刻を持つ。tick を変えないので、途中から始め直さない)。
- 制限: 1ユニットに演出は1つ。続いている途中で、同じユニットに別の演出が来たら、前のものは切れる。
- 続けて起きた軽い演出(回復・強化・能力付与・カウントダウン)は、種類がちがっても1つのまとまりにして、複数のユニットでいっせいに流す(`groupEnd` の `MIX_LIGHT`。設定がオフなら今までどおり種類ごと)。同じ相手に重なったものは、最後のものが出る。

## 破壊の演出のタイミング(11/23)
- 原因: 倒した相手の破壊の演出が、ダメージと別のまとまりになることがあった(間に別のダメージ・能力の表示がはさまる場合。200戦で、破壊1289件のうち38件)。HPが0のまま待ってから破壊が出る/破壊が出直すように見えた。
- 対策: `pullDestroy` で、破壊・消滅のイベントを、その相手に最後にダメージが入った直後へ寄せる(盤面は、ダメージの時点のものを使う)。ダメージ以外(カウントダウン0など)と同じ相手の破壊も、同じまとまりで流す(`groupEnd`)。寄せても別になるのは、間に召喚・ターンがはさまる場合だけ(同じ試験で38件→10件)。

## 進化演出が短くなる(11/23)
- 原因: 再生の待ち時間は `EVENT_MS × mult`(設定「CPUの行動の待ち時間」: 速い≒0.5)だったが、進化・必殺・カウントダウンの動きは長さが固定(CSS)。「速い」にすると、待ち時間だけが短くなり、演出が途中で次に切られた(進化は1000ms→500ms)。
- 対策: `FIXED_MS`(vanish / evolve / finisher / countdown)は、`mult` を掛けない。

## 編成: アミュレットの簡易編成(11/23)
- アミュレットの一覧にも、使用クラスの絞り込み・クラスの見出し(これは前からあり)に加えて、簡易編成を追加。アミュレット枠を開き、「簡易編成」→入れたい順にタップ(最大2つ・タップで外せる)→「この順で入れる」。いまのアミュレットは、選択済みで始まる。クラスが合わないものは、確定時に理由を出して入れない。

## アミュレットのステータス(11/23)
- アミュレットは、速度以外のステータス(HP・攻撃・防御など)を持たない扱い: ステータスの再計算(`recalc`)で、速度以外は基礎値のまま(バフ・デバフ・クラス特性「防御+18%」が効かない)。能力の `buff` も、速度以外はスキップ(演出・ログも出さない)。速度は、いままでどおり変わる。
- 対象の種類は、もともと「ユニットすべて(`scope: unit`)」のときだけアミュレットを含み、フォロワー・キャラクター対象には含まない(変更なし)。
- 編成一覧のアミュレットは、ステータス欄に、速度(とカウントダウンがあればその数)だけ出す。

### マーズ【ファンファーレ】の流れ(11/27)
- ログ(召喚する旨)→ 召喚 → 【常時】の緑の光(ナイト3体ぶん、約0.13秒ずつずらして重ねる)。光りはじめて約0.16秒後に、左のログが出て、強化がはじまる(光りながら、同時に強化開始)。強化の数字が変わるのは、光りはじめて約0.25秒後。
- 緑旗がつく能力が続けて働くときは、`groupEnd` でひとまとめにする(光のあいだに強化が待たされない)。
- 【常時】の3回は、ひとまとめにしない(11/27 追加の動画)。再生は「性能に書いてあるとおり」に従う: ギルダリアは「2体を召喚」と書いてあるので同時。マーズは「3体を強化」ではなく、「それは+200 / これは+100する」が、ナイトが出るたびに1回ずつ働く。そのため `reorderBoost` は、別の回の能力の表示でまとまりを区切る(1回ぶん = 能力の表示 → ナイトの強化・自身の強化(同時)→ 突進付与)。次の回は、強化の終わりを待たず、前の回の約0.31秒後に始める(`REPEAT_FLAG_MS`=150ms + 能力の表示160ms)。動画(30fpsで測定): 左のログが 1.67 → 2.00 → 2.30秒、炎の山が 2.03 → 2.30秒前後 → 2.55秒(間隔 約0.3秒)。炎は、ログの約0.13秒あとに始まる。以前の「約0.14秒ずつ」は読み違いだった。
- 能力付与(keyword)のエフェクトは廃止。強化(buff)のエフェクトと同じ(`BuffFx`)にした(水色の枠・✦は出さない)。
- 召喚された直後のユニットが得る能力(マーズの【常時】の【突進】)は、エフェクトなしで、召喚した瞬間から付いている。`foldEnterKeywords` が、召喚の出来事の盤面に能力を足して、能力付与の出来事は取り除く(同じターンの中のものだけ)。
- 強化の文字(「攻撃アイコン+200」など、カードの上に浮かぶ表記)は廃止(11/27)。強化のエフェクト(`BuffFx`)だけを出し、数字の変化はカードの数字(強化の数字が変わる瞬間)で見せる。
- ユニット(盤面のカード)の下の並び(11/27): 名前 → HPバー → [HPアイコン]HP数値 → [攻撃アイコン]攻撃数値。数値は左寄せ(下の中央に出るアイコン(旗・鎌)と重ならないように)。攻撃力が上がっているときは緑。
- 強化の数字が変わるタイミングは、強化の演出(`BuffFx`)に合わせる: 演出がはじまって約0.12秒後(弧が回りはじめ、光の筋が落ちはじめる時)に数字が変わる(`BUFF_APPLY_MS`)。旗の光のあとに続く強化でも、先の旗の光からは約0.28秒後(0.16+0.12)になり、動画(約0.25秒)に近い。
- 再生は、これから「性能に書いてあるとおり」(11/28)。動画に合わせて並べかえる処理(同じ能力を先に並べる `hoistRepeats`、続く能力のひとまとめ)はやめた。エンジンの出来事の順のまま流す。動画から取り入れるのは、見た目(光・強化の演出)とテンポ(長さ)だけ。

## 強化の数字は演出と同時に上げる(マーズ)
- 原因: 再生用の盤面記録(`emit` のスナップショット)に攻撃・防御・速度が入っておらず、画面は常に最終値を出していた。強化前の数字を見せる処理が空振りしていた。
- 対応: スナップショットに `atk/def/spd` を追加。強化(buff)は、反映後の数字を記録する(`recalc` してから `emit`)。
- 画面: 強化のまとまりでは、`BUFF_APPLY_MS` まで強化前の数字を見せ、BuffFx が動きはじめると同時に数字が上がる(数字のカウントアップは既存の `transform/opacity` 以外に触れない)。

## 強化エフェクトの作り直し(動画 11/27 のルミナスナイトの白い強化を、30コマ/秒で1コマずつ確認)
